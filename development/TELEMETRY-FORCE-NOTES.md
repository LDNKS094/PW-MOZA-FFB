# bridge 发了什么，为什么 PW 可能比 AC7 更重

## 职责

```text
游戏运动状态 → bridge 校验/估算/换成 DCS 字段 → Cockpit 力反馈模型与预设 → 底座
```

bridge 不发送电机力矩，没有 PW 专用“力矩放大倍率”，也不调用底座 SDK。但它并非原样转发：速度向量、G、角速度和攻角/侧滑含估算与滤波。因此 bridge 的估算方法会改变 Cockpit 的输入，间接改变最终杆力。

## 当前实际发送字段

来源：`src/bridge/FlightTelemetry.cs`，经 `CockpitOutput.cs` 推送到本机 TCP 3476。

| 字段 | 单位/含义 | 来源 |
| --- | --- | --- |
| aircraft_name | PW Default | 固定身份，用于预设匹配 |
| acc_x / acc_y / acc_z | G；前向 / 法向 / 侧向比力 | 重建速度求导、补偿重力、转到机体轴、滤波/限幅；不是游戏原生 G 字段 |
| vector_velocity_x/y/z | m/s，DCS 世界轴 | 游戏前向速度给大小，修正后世界位移给方向，再交换 UE/DCS 轴 |
| tas / ias | m/s | 两者都用游戏速度代理，与 AC7 参考相同；不是真实空速系统 |
| vertical_velocity_speed | m/s | 重建速度的垂直分量 |
| heading / pitch / bank | rad | 游戏姿态由度转弧度 |
| euler_vx / euler_vy / euler_vz | rad/s；roll/yaw/pitch 对应项 | Euler 姿态差分、环绕修正及滤波；不是严格的机体角速度传感器 |
| aoa / aos | 度，估算的攻角/侧滑 | 轨迹速度相对于机体方向的角度，包含采样相位/滞后，不是真实气流测量 |

当前不发送转速、油门、加力、武器、弹药、起落架、高度、Mach 等字段；不是声称它们实际为零，而是尚未接入。失效时已发送的运动字段回到中性值：速度为零、法向 1 G、其他动态分量为零。

## G 是怎么计算的

先重建世界速度：

```text
v = 游戏前向速度 × normalize(本次修正世界位置 − 上次位置)
a = (v_now − v_previous) / 游戏时间差
比力 = a − 重力向量
机体 G = dot(比力, 相应机体方向) / 9.81
```

世界 Z 向上，所以代码向 a_z 加 9.81；平飞无加速时法向约 1 G。重复位置、长间隔、暂停、会话变化或明显跳变不参与正常求导。

当前前/侧向限制 ±4 G、法向 −4～12 G，滤波时间常数 0.12 s；角速度滤波 0.08 s。这是输入清理/参考限制，不是桥接在计算或指定电机力矩。

## 与 AC7 的真实差别

| 项目 | AC7 参考 | PW |
| --- | --- | --- |
| 速度来源 | `GetVelocity()` × AC7 专用比例 10，按 cm/s 传入桥接 | GetVelocity 全零；用前向速度大小 + 实际位移方向重建，协议使用 m/s |
| 差分时间 | bridge 的单调接收时间 | 游戏采样时间；另以真实时间检查停顿 |
| 计算调度 | TCP 发送循环选 latest 后计算 Frame | 每个新输入先计算，TCP 循环发送缓存帧 |
| G 投影/滤波 | 补偿重力、投影，0.12 s；前/侧 ±4，法向 −4～12 | 同样投影、滤波常数和 G 限制；另拒绝异常跳变与重复位置 |
| 姿态角速度 | 姿态差分、0.08 s 滤波 | 同类算法，增加合理范围限制和历史复位 |
| TAS/IAS | 游戏速度代理 | 游戏速度代理 |
| 其他 DCS 字段 | 发送估算 RPM/加力、固定高度 3000、Mach 等占位/估算 | 未验证字段省略 |

AC7 的比例 10 是其现有速度源适配，不应照搬到 PW，也不能仅凭该常数判断谁的物理标定正确。两边数据来源和采样时钟不同，即使公式/预设相同，得到的 G 也不必相同。

尤其注意：AC7 明确发送固定 `h_above_sea_level=3000`，PW 目前不发送高度。如果 Cockpit 使用高度修正空气密度，或者对缺失字段保留上次值/使用默认值，这也是潜在差异；其具体行为没有独立验证，不能直接认定某个固定放大比例。

## 新增 AC7 采集：高 G 能力与机动分布

报告和数据目录：`../AC7-MOZA-FFB/development/artifacts/telemetry-capture/session-20261102-115535-5992672/`，主报告 `REPORT.md`，核对文件 `replay.json`、`core-analysis.json`、`ac7-posture-subsets.json`。

这轮直接引用 AC7 生产 Parse/Frame，采集真实飞行驱动的诊断发送循环，不连接 Cockpit 或设备；14725 条输入、6883 条完整输出，4936 条有效飞行输出。按原选样顺序和 Sample.t 回放，6883 帧字符串不一致为 0。它比低频心跳可靠，但隔离诊断环境不保证与正常 Cockpit 运行的线程调度相同，也没有测到底座力矩。

已核对的 AC7 数值：

- 约 600 km/h 的稳态片段，法向输出精确 1 G。
- 大坡度正 G 转弯窗口（推断窗口，非人工标记），速度中位约 3230 km/h、坡度中位约 72.3°，法向 G 中位 10.4467、95% 分位 11.6676。
- 小坡度转向的法向 G 中位约 1.01/1.09，但侧向 G 中位约 −3.57/+3.50；不是“转向时完全没有载荷”。
- 向量速度长度/标量速度比例中位 1.000116、范围约 0.998873～1.002347，未见 100 倍或 3.6 倍的内部单位错配；这不是独立物理标定。

两轮的姿态分布对比（只作描述，不是同工况标定）：

| 分组 | AC7 本轮诊断实际输出 | PW 既有记录按当前公式重建 |
| --- | --- | --- |
| abs(roll)<5° 且 abs(pitch)<3° | 占有效帧 53.75%，法向 G 中位 1 | 占 5.16%，法向 G 中位 1 |
| abs(roll)>45° | 占 20.58%，法向 G 中位 9.1483 | 占 53.18%，法向 G 中位约 8.45 |

PW 分组数字来自 AC7 agent 的独立重建报告；AC7 分组已核对 JSON。AC7 机动主要在约 3000 km/h，而 PW 既有数据速度中位约 840 km/h，且没有匹配转向率和完整轨迹。因此不能把上表读成“AC7 一定更强”或“PW 算法没问题”。

**目前更有证据支持的解释是：工况及载荷轴向分布不同，而不是 PW 隐藏了统一 G 放大倍率。** AC7 本身明确能输出 10～12 G；两轮混合中位数不能用来证明 PW 放大。若视觉动作似乎相同，还应核对实际采样姿态、输入模式与轨迹，而不是仅凭操纵杆动作命名机动。

仍未独立隔离：速度方向重建误差、采样时钟、逐输入与逐发送求值、缺失字段在 Cockpit 中的默认语义。下一步优先从两份原始数据匹配实际速度、轨迹曲率及机体姿态；若没有同速机动窗口，再只补约 800 km/h 的受控片段，不先改比例系数。

## 新版采集准备：先抓实际发送，再分析轻拉

旧数据的输入回放与约 1 Hz 游戏心跳都不足以还原实际发送起始峰值；未准备好采集之前，不应要求用户再测。现已在现有 bridge 内加入逐写入日志，仍用 `payload/DCS.exe`，不增加第二套转换。`frames.jsonl` 保存实际完整帧、原始输入关联、共享单调时间、状态及写入结果，覆盖重复缓存、过期与最后中立帧；记录路径和有效性检查见 [TELEMETRY-CAPTURE.md](TELEMETRY-CAPTURE.md)。

本轮不改 `FlightTelemetry.cs`、Lua 或 preset。生产管道/转换/随机 TCP 的自动联调已通过；真实新版采集和电机行为尚未验证。版本/源码散列与程序快照供追溯，后台队列丢失或 I/O 故障明确判记录不完整；写入成功不代表 Cockpit 已解析。也未采集物理杆位，所以不能量化小杆量增益或精确操纵输入延迟。

## 怎么理解“相似机动”

相同拉杆幅度、近似视觉动作，不代表两款游戏的速度、转弯角速度、载荷相同。仅向心加速度的量级就与 `速度 × 轨迹转向角速度` 有关；速度更高或转向更急，会得到更大的 G。

**杆力不是只由加速度决定。** Cockpit 收到的还有空速代理、角速度、姿态、攻角/侧滑等；如何混合取决于其模型和预设。典型气动载荷还与动压有关，但不能把一般物理公式冒充 Cockpit 已验证的内部实现。

目前已有 AC7 原始输入与诊断发送记录，但还没有与 PW 同速度、同转向角速度的匹配片段，也没有做效果逐项开关对照，所以不能把差异全归因于游戏或全归因于 bridge。下一步若要校准，应先比较两边实际发送的 IAS/TAS、G、角速度及缺失字段语义，再单独测试 Cockpit G 效果；不要先给 PW 随意加一个缩放系数掩盖问题。
